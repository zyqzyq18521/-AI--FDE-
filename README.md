# 赋范AI课堂-FDE 企业项目实战训练营
获课：jzit.top/26291/


FDE 做性能压测，最容易踩的坑是把“压测”当成一个独立环节：跑个脚本，看个报告，交差。但客户现场的真实情况是，压测脚本写得好不好，取决于你对业务链路的理解深不深；瓶颈定位准不准，取决于你有没有一套从“全局指标异常”到“根因穿透”的排查路径。这两件事串起来，才构成 FDE 压测实战的完整闭环。

**压测脚本的设计，核心不在脚本语言，在“请求像不像真人”。**

FDE 压测脚本的第一条原则是**贴近真实用户行为**，而不是把并发数拉满。一个电商场景的压测，如果所有虚拟用户都请求同一个商品 ID，数据库连接池和缓存命中的表现会严重失真。有效的脚本设计需要做参数化：用户 ID、商品 ID、搜索关键词从数据集里动态取，而不是写死。阿里云 PTS 和腾讯云 PTS 的脚本模式都支持出参定义，登录接口提取 token 传递给后续接口，列表接口提取 itemId 传给详情页，这样链路才是串联的、有状态的。另一个常被忽略的点是思考时间：真人在页面之间会停顿、会犹豫，脚本里不加等待时间，压出来的 QPS 是虚高的，上线后真实流量一进来，系统表现完全对不上。FDE 在客户现场写脚本时，宁可把并发数设低一点、把行为模拟得真一点，也不要拿一个失真的高 QPS 去汇报。

**压测执行的第一步不是跑脚本，是确认“压测机本身不是瓶颈”。**

一个反复被验证的教训是：压测结果难看，不一定是被测系统的问题，可能是压测机先撑不住了。压测机 CPU 超过 70% 时，结果就不可信了。FDE 在正式压测前应该先确认两件事：压测机和被测机分开部署，避免资源争抢；压测工具本身用非 GUI 模式运行，避免图形界面消耗资源。基线采集阶段用阶梯加压而不是一次性拉满，观察 P95 响应时间和错误率随并发上升的变化曲线，找到拐点比找到最大 QPS 更有价值。拐点之前的数值才是系统能稳定承载的范围，拐点之后的数字只是压垮系统的证据。

**瓶颈定位的关键能力，是从“哪个进程 CPU 高”跳到“为什么这个函数被反复调用”。**

FDE 在客户现场听到“系统太慢”，第一反应不该是加内存或扩机器，而是找那个拖垮全局的单一瓶颈点。全局指标扫描看三样东西：CPU 持续超过 90% 的进程、内存突增的进程、处于不可中断睡眠状态的进程。确定瓶颈域之后，CPU 高用 perf 看热点函数，内存高看线程堆栈，IO 高看 iostat 的 await 是否超过 100ms。但这里有一个更深层的教训：火焰图最宽的路径不一定就是全部答案。APISIX 的一次吞吐回退排查中，火焰图显示最热的两个位置合计只占 6.9%，真正的问题藏在调用频率被放大的地方，一个只占 3% self time 的函数，因为每个请求被调用了几十次，累计成本远超预期。FDE 定位瓶颈时，**看宽度也要看调用次数**，一个窄但高频的路径，杀伤力可能比一个宽但低频的热点更大。

**AI 链路的压测要额外做一件事：把模型调用和基础设施分开测。**

FDE 交付的项目越来越多涉及 AI 功能，压测逻辑需要分层。模型调用本身的延迟（几秒到几十秒）会掩盖基础设施的真实表现，如果直接把包含真实模型调用的链路拿来压测，你测到的是“模型有多慢”，而不是“你的系统能扛多少并发”。有效的做法是在压测基础设施层时用 mock 替代真实模型调用，返回预置响应并模拟流式延迟，把平台层的 QPS 上限单独测出来。然后再用小比例的真实模型调用压测端到端延迟，评估用户在真实场景下的等待时间。这两组数据分开看，才能判断瓶颈到底在模型供应商那边，还是在自己的服务编排和连接池上。

归根结底，FDE 压测实战的功夫不在脚本语法里，在三个判断上：脚本的请求够不够真、压测机有没有先垮、瓶颈定位是停在“哪个进程热”还是挖到了“为什么热”。工具会换，平台会变，但这三层判断力是换什么环境都带得走的。压测报告上的数字只是结果，定位问题的路径才是能力。
